# 竹萌设计理念纲要

## 总体框架

竹萌的服务器设计由城邦、荒野、经济和基础事件框架共同组成。城邦提供玩家身份、组织关系和长期建设目标。荒野提供主要产出、冒险风险和有限冲突空间。经济系统负责把建设、冒险、战争和组织治理转化为可计算的投入产出关系。基础事件框架由`ImyvmWorldGeo`承载，为上层系统提供空间、时间、事件和统计能力。

城邦与荒野的关系是本设计的主轴。玩家可以从城邦获得身份、资源支持和社会关系，也可以以个人身份进入荒野活动。城邦不能成为跳过生存发展过程的捷径，荒野也不能成为短周期自动刷取高价值资源的渠道。服务器机制需要让个人、庄园和领域都能参与冒险与竞争，但大规模组织收益要承担更高治理成本和响应成本。

## 城邦体系

该框架由`WorldGeo-CommunityAddon承载`。城邦体系的核心价值在于给予玩家稳定的社会身份，引导建设、贸易、治理和协作行为。城邦作为经济行为的落点，承载国库、成员政策、建设回馈、身份展示和对外互动。城邦内部与城邦之间的关系应当形成可被玩家感知的社会结构，使服务器世界具有长期演化的组织氛围。

城邦体系的限制在于，玩家不能通过加入城邦跨过大多数升级步骤。同一个城邦不能成为所有玩家的唯一最优选择，城邦规模越大，治理、福利、土地和战争响应的成本越高。竞争机制不能让大城邦在所有维度上形成碾压优势，小组织和个人仍应保留可进入的活动空间。

## 荒野体系

该框架由`WorldGeo-AdventureAddon承载`。荒野承担服务器经济的主产出功能。荒野产出略高于原版属性的物品、趣味道具、四级兑换货币和金钱。荒野也是冒险玩法、开放世界遭遇、固定场地小游戏和有限攻击性行为的主要空间。

荒野的限制来自资源、自动化和冲突边界。高价值资源不能在短周期内被快速刷取。全自动方法不能稳定取得高档收益。玩家和城邦之间的格斗行为需要被控制在规则化空间、规则化窗口和可结算目标之内。

## ImyvmWorldGeo 基础事件框架

`ImyvmWorldGeo`承担服务器的空间、时间、地理解析和事件统计底座。附加mod通过接口读取空间归属、空间设置、周期时间、行为事件和统计快照，并在各自业务层解释这些数据。底层框架的职责是提供稳定对象、稳定事件和稳定查询能力。

`ImyvmWorldGeo`不得在领域模型、配置项、事件名或持久化结构中出现城邦、庄园、领域、野区、战争、研究等上层语义。下层只承认空间、主体、行为、时间、设置、统计和效果。上层需要专用规则时，应通过命名空间扩展键、空间标签、事件订阅和只读查询组合完成，并在上层项目中解释这些通用事实。

### 空间对象

空间对象由Region、GeoScope和SubSpace组成。Region是上层语义可以引用的区域单位。GeoScope是在空间上组成Region的基础范围。SubSpace附加在GeoScope之下，用于表达更细颗粒度的空间对象。

特定坐标的任何元素依靠其坐标与空间对象的关系受到行为影响。空间对象在(x,z)组成的平面投影坐标系上占有范围，并以该范围为基础包含垂直方向上任何(x,z)落在此范围内的点。一个坐标要么属于GeoScope，要么不属于GeoScope。SubSpace的范围必须严格位于某个GeoScope内。

Region、GeoScope与SubSpace需要拥有稳定编号、人类可读名称、几何范围、维度归属、进入离开事件、坐标归属解析、空间内玩家枚举、空间事件广播、空间统计快照和键值化设置项目。键值化设置项目由名称、值、类型、修改时间和修改主体构成。空间标签以字符串集合或键值集合存在，用于表达上层系统对该空间的选取、用途或通用行为要求。标签本身只表达通用分类，不在WorldGeo中解释收益、身份或战争规则。

空间对象以设置项目发挥效果。权限类设置项目针对玩家主动实施的操作。规则类设置项目对区域内客观世界机制全量应用。效果类设置项目对玩家被动应用状态效果。通用行为包括进入提示、离开提示、PVP开关、方块交互权限、实体伤害权限、传送许可查询、地图渲染颜色、周期统计启用状态和公告广播范围。

SubSpace以类似GeoScope的方式创建、修改、查询、删除和管理，默认名称为SS-{序号}，并具有编号和默认进入消息。进入消息需要以前缀标明其不同于GeoScope的性质。修改GeoScope范围时，系统需要检测是否造成SubSpace溢出原范围。一切对GeoScope应用的地理框架内容，在SubSpace条件允许时应等量应用到SubSpace。

### WorldGeo 对外 API 设计

WorldGeo稳定对外接口分为只读查询、受控写入、事件订阅和服务查询四类。上层mod不得直接依赖WorldGeo的infra、application或mixin包，也不得通过可变领域对象绕过持久化和回滚流程。

#### 空间查询 API

空间查询API用于让上层读取空间事实。

1. `getRegion(id)`、`getRegionByName(name)`、`listRegions()`和`listRegionsByMark(mark)`返回Region快照或受控只读对象。
2. `listScopes(regionId)`、`getScope(scopeId)`和`getScopeByName(regionId, name)`返回GeoScope信息。
3. `listSubSpaces(scopeId)`、`getSubSpace(subSpaceId)`和`getSubSpaceByName(scopeId, name)`返回SubSpace信息。
4. `resolveAt(world, x, y, z)`返回最具体空间归属，结果包含Region、GeoScope和可能存在的SubSpace。若调用方只关心平面归属，可以使用`resolveAt(world, x, z)`。
5. `getShape(spaceId)`、`getArea(spaceId)`、`getWorldId(spaceId)`和`getDisplayName(spaceId)`用于菜单、地图、结算和调试。

这些API返回的数据不能允许调用者直接修改数据库对象。需要修改时必须走受控写入API。

#### 空间写入 API

空间写入API用于创建和修改通用空间对象，并负责校验、保存、失败回滚和兼容旧数据。

1. `createRegion(player, name, idMark, shape)`创建Region及首个GeoScope。`idMark`只作为上层命名空间标记，WorldGeo不解释其业务含义。
2. `addScope(player, regionId, name, shape)`、`replaceScopeShape(player, regionId, scopeId, shape)`、`transferScope(player, sourceRegionId, scopeId, targetRegionId)`和`deleteScope(player, regionId, scopeId)`处理GeoScope生命周期。
3. `createSubSpace(player, scopeId, name, shape)`、`replaceSubSpaceShape(player, subSpaceId, shape)`、`renameSubSpace(player, subSpaceId, name)`和`deleteSubSpace(player, subSpaceId)`处理SubSpace生命周期。
4. 所有形状写入必须验证维度一致、范围合法、面积限制、同层空间冲突和SubSpace不溢出父GeoScope。
5. 所有写入必须在Minecraft服务器线程执行，失败时恢复内存对象和文件状态。

#### 设置与标签 API

设置API用于通用空间规则。权限类设置管玩家主动行为，规则类设置管客观世界机制，效果类设置管玩家被动状态。

1. 内建权限、规则和效果由WorldGeo维护。
2. 上层可以注册命名空间扩展权限和规则，例如`community:plot_trade`或`adventure:war_window_teleport`。WorldGeo只存储和解析布尔值，不解释业务含义。
3. 设置优先级为SubSpace、GeoScope、Region；同一层内个人设置优先于全局设置。
4. 标签API提供字符串标签和键值标签的增删查改。标签用于筛选空间，不触发任何底层业务逻辑。

#### 时间服务 API

时间服务API由WorldGeo或Hoki承载，但对Community和Adventure提供同一套语义中立查询。

1. `getGameTime(world)`返回游戏tick、游戏日、日内时间、天气和月相。
2. `getRealTime(zoneId)`返回UNIX time、时区、自然小时、自然日、自然周、自然月和自然年。
3. `subscribeCycle(cycleType, zoneId, listener)`允许上层订阅小时、天、周、月切换。
4. 所有周期边界以配置时区为准（默认东八区），并在服务器启动时从真实时间补算错过的周期，但不得重复结算同一周期。

#### 行为事件 API

行为事件API记录原版Minecraft事实，不解释上层收益。

1. 原始事件字段至少包括事件ID、玩家UUID、时间戳、维度、坐标、Region、GeoScope、SubSpace、行为类型、行为对象、数量和原版事件来源。
2. 行为类型包括方块放置、方块破坏、实体伤害、实体击杀、玩家死亡、容器交互、物品使用、进入空间和离开空间。
3. 事件通过Fabric事件、mixin或服务端tick监听进入WorldGeo infra层，再转换为WorldGeo通用事件。
4. 上层可以订阅事件流，也可以查询已聚合统计。订阅回调不能阻塞服务器tick，复杂处理应写入上层队列。

#### 统计 API

统计API按小时、天、周和月归并事件。

1. `queryEventStats(spaceId, cycle, filters)`返回通用事件聚合。
2. `queryBlockDelta(spaceId, cycle, blockFilter)`返回方块放置量、破坏量、净增加量和玩家贡献分配。
3. `queryResidence(spaceId, cycle)`返回区块加权栖息时间、平均栖息时间和总栖息时间，时长以毫秒计。
4. `queryEntityCombat(spaceId, cycle, filters)`返回伤害、击杀、死亡和被伤害事实。
5. `queryOnlineTime(spaceId, cycle, filters)`返回玩家在线时长与AFK时长。连续5分钟无移动且无输入计为AFK；非AFK在线时长为在线时长减去AFK时长。
6. 统计层只输出事实，不输出建筑收益、冒险收益、战争分或税额。

#### 菜单与玩家交互 API

玩家交互API用于让上层模块取得语义中立的展示能力，而不是取得WorldGeo内部菜单对象。WorldGeo只提供空间事实、提示通道和通用开关，上层模块负责解释按钮含义、权限和后续业务动作。

1. `getSpaceSnapshot(spaceId)`返回用于菜单展示的空间快照，包含稳定编号、人类可读名称、维度、面积、主导地貌、父子关系、进入离开提示状态、关键通用设置摘要和地图颜色建议。
2. `listSettingSummaries(spaceId, viewerAccess)`返回按WorldGeo中立可见级别过滤后的设置摘要；内置级别为`PUBLIC`与`OP_DEBUG`，用于列表lore、详情页和操作确认，底层存储对象保持在WorldGeo内部。WorldGeo不定义社区管理者、组织管理者或战争管理者身份。
3. `toggleLocationActionBar(player)`、`setLocationActionBarVisible(player, visible)`和`isLocationActionBarVisible(player)`提供位置行为栏开关，行为栏只展示当前位置、空间名称和通用状态。
4. `sendSpaceMessage(spaceId, messageKey, args)`提供空间范围广播，消息参数使用本地化key和通用对象，Community或Adventure领域对象由各自模块转换为通用展示参数。
5. `openSpaceDebugView(player, spaceId)`只面向OP或服务器调试权限，用于查看空间事实、设置来源和统计版本；上层玩法结算公式保留在对应上层模块。

这些API提供语义中立的空间能力。上层若需要在菜单中显示收益、战争、组织身份或管理者视图，应先读取WorldGeo空间事实，再在上层模块中判断业务身份并组装玩家可见内容。

#### 信息分层与保密展示

所有玩家交互都分为玩家可见、管理者可见、OP可见和系统私有参数四层。玩家指普通玩家；管理者指对应行为所属社区、组织或玩法机制的管理人员；OP指服务器管理人员。该分层只影响信息发送。WorldGeo作为底层空间能力只内置`PUBLIC`与`OP_DEBUG`两类可见级别，管理者可见层由Community或Adventure在各自业务模块中判断。玩家可见层展示当前状态、可执行动作、成本、风险范围、结算结果和下一次可操作时间。管理者可见层增加组织余额、权限、审计流水、成员汇总和公共收益。OP可见层增加配置、异常队列、失败重试、数据修复和调试状态。系统私有参数包括随机种子、精确公式、风控阈值和反刷权重，只存于服务端持久化与配置，不加密，但绝不出现在任何下行消息、菜单lore和提示中。

箱子菜单、聊天可点击消息、行为栏和进入离开提示必须使用同一套信息分层。箱子菜单提供完整操作闭环和确认页；可点击消息提供同等入口、摘要和跳转；行为栏提供当前位置或当前状态的轻量提示；进入离开提示用于空间状态变化。任何消息都应写清操作者、空间、主体、金额、操作内容和结果，并且只展示查看者权限范围内的事实。

### 地理空间解析

地理空间解析对Region及其GeoScope进行自然地理和人文地理衡量。解析发生在服务器加载、GeoScope范围创建或更新、现实世界每周开始等节点。

涉及平均指数的地理解析以GeoScope所涉及的区块集合为对象。对于每个区块，在其中属于GeoScope的坐标上随机抽取一点，以该坐标情况代表区块情况，然后根据每个区块在GeoScope中的坐标数量加权计算各项指数。

#### 自然地理的平均指数

自然地理用于描绘空间对象的景观氛围，并基于景观氛围自动计算空间对象的风土。气温和降水确定气候，气候与生物群系相互联系。地区还具有高度特征，并相对于确定的地理衡量坐标系具有方位特征。

主世界生物群系粗糙归类为海洋（含河流、沙滩）、平原、沙漠、森林、山地、雨林（含红树林与泽地）和雪地。系统统计各类比例。海洋为主导群系时直接标记海洋。海洋不是主导群系时，排除海洋后判断剩余主导群系。没有单一主导群系时，如两种类型合计达到总面积70%，则以两种类型共同作为主导群系。仍不能归类时，标记为多元区域。

下界和末路之地直接以所在维度标签作为地理属性。主世界GeoScope需要确定平均海拔，水域海拔以水面确定。GeoScope几何重心用于确定方位。以坐标原点为中心延伸出X、Z主轴，重心离任一轴距离小于等于2000格时，视为在该方向正位上。Region的地理属性以面积最大的GeoScope为准。

#### 人文地理

人文地理用于刻画玩家行为。栖息时间和玩家放置破坏方块统计是两个可用代理变量。

栖息时间按区块计算。同一区块一起加载卸载，因此同一区块内栖息时间一致。栖息时间计算包括GeoScope或Region的平均栖息时间，以及总累积栖息时间量。总累积栖息时间量由平均栖息时间乘以总面积得到。

玩家放置或破坏方块统计通过带有时间戳、实施主体、实施对象的条目整合。各现实世界自然周期需要统计玩家在特定区域内对各项目的方块放置量，也要统计这些方块被各种形式破坏的量，尤其是玩家对各种方块的破坏量。单个玩家在特定GeoScope或Region的周期净放置量，以区域内该种方块的净增加量为上限，再按玩家分别净放置量加权分配。

### 时间服务

时间服务同时处理Minecraft内时间系统和现实世界时间系统。

Minecraft内时间系统需要捕捉游戏刻、由游戏刻推算的天数、一天之内的时间性质、天气和月相信息。现实世界时间系统需要基于输入时区和服务器存储的UNIX time，提供当前时区基准和时间，并据此提供自然小时、天、周、月和年度周期基准。

### 事件与统计能力

主体行为记录以玩家、时间、位置、行为类型和行为对象为基本字段。方块放置、方块破坏、实体伤害、实体击杀、死亡、容器交互、物品使用、玩家移动进入空间、玩家离开空间，都应当在可配置范围内形成统一事件。

统计层按小时、天、周和月归并事件，输出给上层系统读取。上层系统据此计算建设收益、冒险收益、战争贡献、区域热度和反机械刷取指标。事件与统计能力不解释建设、冒险或战争收益，只提供可查核的行为事实和周期聚合结果。

### 原版交互边界

附加mod与Minecraft原版交互时，应把监听、拦截和物品改写集中放在各自infra模块。原版事件进入附加mod后，应先转化为通用领域事件，再进入收益、权限或状态计算。空间框架和玩法框架据此保持清楚边界。

WorldGeo自身与原版代码交互时，Fabric API事件优先于mixin；只有Fabric API无法覆盖的行为才使用mixin。mixin只负责截获原版事实或阻断通用权限与规则，不写入Community或Adventure语义。上层项目与原版交互时也应遵守同一规则：listener/mixin位于该项目infra或entrypoint层，业务层只接收本项目定义的领域事件。

## 代码与编程技术标准

以下纳入总则。

1. 代码分工明确。附加mod所有实现应当优先到ImyvmWorldGeo寻找合适的轮子，而不要优先自己去搓轮子。
2. 不要过度耦合。不要在更底层项目的代码或文档中有意体现出更上一层项目的存在或者任何相关对接需要。更底层项目要作为抽象、独立、可脱离更上层项目的轮子存在。
3. 少使用使用兜底、简单、具体的实现，修改代码要考虑程序抽象的运行框架是否还足够清晰、自上而下有序，能否尽可能从抽象的框架层次上，在不影响别的已有机制运行或表现的前提下，进行实现。
4. 要将重点放在菜单设计。菜单以箱子菜单和信息栏可交互菜单两个方面完全同步实现。功能设计必须闭环。每个机制都要写清玩家、社区管理者、OP分别在哪个入口查看、点击、确认和返回。箱子菜单负责完整页面树、按钮、lore、分页、确认和`runBack`；信息栏可交互菜单负责摘要、可点击跳转和结算通知。菜单点击后如需让玩家阅读聊天消息，应先关闭菜单再发送消息。所有展示都要准确表达当前事实、操作成本和影响范围，并按玩家可见、管理者可见、OP可见和系统私有参数分层。
5. 要让玩家看到或键入人类可读的内容，并且在可能的情况下尽可能提供准确的候选项目，如领地的人类可读名称。不要试图让玩家只能键入人类难以理解或输入形式的编码，如特殊符号，长id，配置项形式（如"A项目=B值"）。如有后者，比如扫描代码查到，应更改为可读内容和编码都能输入的形式，但只推荐可读项目形式输入（如提供名称列表）。
6. 从旧版本升级为新版本的对象，比如对象的字段进行了添加的情况下，不要升级数据库版本，而是考虑怎么优化字段存储读取结构逻辑，如在没读取到的时候采取什么方式进行数据覆盖等。最重要的是，不能造成旧有对象因加载失败而被强制删除或覆盖或丢失任何信息，这一点一定要测试到位。
7. 添加功能，特别是跟玩家交互相关的功能，一定要参考已有实现，并且跟用户确认好思路。
8. 与游戏原代码直接交互的行为，要么通过调用别的库，要么放到infra/下专门模块统一实现。
